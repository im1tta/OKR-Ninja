## Context

See proposal.md — Why. Platform discovery, verified against each vendor's docs on 2026-09-23:

| Platform | Reads skills from |
|---|---|
| Claude Code | `~/.claude/skills/`, `.claude/skills/` (start dir up to repo root), enabled plugins, claude.ai account skills. Not `.agents/skills/`. Its listing truncates `description` + `when_to_use` at 1,536 characters. |
| Cursor | `.agents/skills/`, `.cursor/skills/`, `~/.agents/skills/`, `~/.cursor/skills/`, and for compatibility `.claude/skills/`, `.codex/skills/`, `~/.claude/skills/`, `~/.codex/skills/`. |
| Codex | `.agents/skills/` (cwd up to repo root), `~/.agents/skills/`, `/etc/codex/skills`. Follows symlinks. Advises front-loading trigger words because hosts may shorten descriptions. |
| Cowork, claude.ai | Account skills uploaded as a `.skill` archive, or plugins. Cowork ignores a project folder's `.claude/skills/` (tested by the owner). |

The upload format is the one skill-creator's `package_skill.py` writes: a zip whose entries sit under one top-level folder named after the skill. Its `quick_validate.py` rejects a description over 1,024 characters or containing `<`/`>`, a name that is not kebab-case or is over 64 characters, and any key outside `name`, `description`, `license`, `allowed-tools`, `metadata`, `compatibility`. A Claude plugin is `.claude-plugin/plugin.json` (only `name` required) plus `skills/<name>/SKILL.md`, zipped as `<name>.plugin`.

Constraints: stdlib only, like `evals/grader/harness.py`; no git dependency at install time; skill content changes are limited to the frontmatter description.

## Goals / Non-Goals

**Goals:**
- One command installs the skill for every folder-reading platform; one build yields both upload packages.
- The check fails in this repo's verify gate whenever the frontmatter would fail an upload, not first at upload time.
- The installer never deletes a checkout, a clone, or anything a symlink points to; it replaces only what sits at its own two target paths.

**Non-Goals:**
- A general-purpose skill packager: the payload list, the skill name and the two targets are specific to this repo.
- Parsing arbitrary YAML (see D2).

## Decisions

**D1 — One root-level `install.py` with `install` (default), `build` and `check`.** Root level because the README's install route should read `python3 install.py`. One script because install, build and check share the payload enumeration and the frontmatter check; splitting them would duplicate both. Rejected: `install.sh` (no Windows, and Cursor and Codex both run on Windows); `tools/package.py` (less discoverable for the users it exists for); separate build and install scripts (duplicated logic).

**D2 — A strict frontmatter reader, not a YAML parser.** The stdlib has no YAML parser and the script must not need `pip`. The reader takes the block between the first line `---` and the next line `---`, reading the file with universal newlines exactly as the reference validator does (`Path.read_text()`), so CRLF files pass as they would upload — Git for Windows checks files out with CRLF by default. A byte-order mark is refused, because the validator's `startswith('---')` then fails. The block closes at the first line from the third on that begins with `---`, as the validator's `^---\n(.*?)\n---` match does (it cannot close on the line right after the opener); a second `---` right after the opener is YAML's document-start marker and is skipped. A symlinked `SKILL.md` is refused by the check itself, not only by the build and the installer. Tabs anywhere in the block are refused: YAML forbids them in indentation and PyYAML rejects several other placements. With tabs gone, the space is YAML's only whitespace, so blank lines, comments, indentation and trailing whitespace are judged by spaces alone — never by Python's `strip()`, which would also drop no-break and other Unicode spaces that YAML keeps as text. Python's `strip()` is used only where the validator itself uses it: on `name` and `description` before their rules apply. So are characters PyYAML's reader rejects (control characters) and the Unicode line breaks U+0085, U+2028 and U+2029, which YAML would read as line ends inside a one-line value. Top-level keys are unindented `key: value` lines; indented and list lines belong to the preceding key, so a `metadata:` mapping reads as present without being interpreted. `name` and `description` must be single-line scalars: plain, or wrapped in matching single or double quotes (single quotes unescape `''`; a double-quoted value with a backslash is refused rather than unescaped). A plain `name` or `description` that YAML would read differently is refused with the reason: one containing `: ` or ` #` or ending in `:`; one starting with an indicator character (`,`, `[`, `]`, `{`, `}`, `#`, `&`, `*`, `!`, `|`, `>`, `%`, `@`, `` ` ``, or `-`/`?`/`:` followed by a space); and one matching PyYAML's implicit non-string resolvers (booleans including `yes`/`no`/`on`/`off`, null, integers and floats including signed hex, octal, binary and sexagesimal forms like `1:30`, timestamps like `2026-09-23`, and the `=` and `<<` tags). `license`, `allowed-tools` and `compatibility` must be one-line values passing the same scalar rules, except that a trailing ` #` comment is allowed there (it is stripped first, as YAML does); flow collections such as `[Read, Grep]` are refused rather than parsed — write them as plain strings; an empty value reads as null, which the validator accepts; indented or list lines below any of them are refused. `compatibility` must be a string of at most 500 characters, measured as the validator does (unstripped). `metadata` is the only key that may have lines below it, and only in the shape the Agent Skills spec defines — a map of string keys to string values: indented `key: value` lines at one indentation, each key and each value passing the scalar rules (so `<<`, `*a`, `'a`, `2026-02-30` or `1` as a key is refused); anything else under it is refused. That is the whole accepted subset. The promise is two-sided and no wider: every form inside the subset gets exactly the rules uploads enforce, and every form outside it is refused. The reader is not a YAML parser and does not claim to mirror arbitrary YAML. Lengths are counted in characters after stripping surrounding whitespace, as the upload validator does.

**D3 — The payload is enumerated from the filesystem.** `SKILL.md` plus a sorted recursive walk of `references/` and `examples/`, taking regular files only: names beginning with `.` are skipped at every level, as are `__pycache__` folders, `*.pyc` files and Windows folder metadata (`Thumbs.db`, `desktop.ini`); a folder that cannot be read stops the run with the folder's name rather than being silently skipped, and every payload file is read into memory before anything is written, so an unreadable file stops the run before a folder is created; symlinks are skipped rather than followed, so nothing outside the checkout can ship. No `git ls-files`, because the installer must work from a downloaded archive. Consequence: an untracked file dropped into `references/` or `examples/` would ship. `build` and `install` print the payload file count and `build` lists every entry, and verify compares the built entries with `git ls-files`.

**D4 — Reproducible archives.** Entries are added in sorted order, files only (no directory entries, matching `package_skill.py`), each with the zip epoch timestamp (1980-01-01 00:00), mode `0644`, and `ZIP_DEFLATED` at a fixed compression level. Each archive is written to a temporary file in the output folder and moved into place, so an interrupted build never leaves a truncated package under the final name. Byte identity holds across rebuilds on one machine; a different zlib may compress differently, which the spec does not require.

**D5 — The plugin manifest carries no new product text.** `name` comes from the frontmatter; `description` is the first sentence of the frontmatter description (up to the first `. `), so SKILL.md stays the only owner of what the skill says it does; `version` is a `PLUGIN_VERSION` constant in `install.py`, starting at `0.1.0`, bumped when a changed payload is shipped to plugin users. No `author` or `repository`: both are optional, and the repository URL is still a placeholder in the README.

**D6 — Install validates everything, then replaces each target through a staging copy.** Before writing anything, the installer runs the check, resolves every target, and refuses on any conflict (spec: Replacing an existing install is safe), so a refusal never leaves one target updated and the other not. For each target it copies the payload into a hidden staging folder beside the target (same parent, so the final move stays on one filesystem), then swaps it in: the target — a real directory, a symlink or a junction alike — is renamed aside to a hidden sibling (made owner-writable first on POSIX, because macOS will not move a folder its owner cannot write; the mode is restored if the swap is undone); the staging folder is renamed into place; only then is the old copy deleted. A failure before the swap leaves the old copy where it was (if the second rename fails, the first is undone — which restores a link exactly, because the link itself was moved; if undoing fails too, the error names where the previous copy was left); a failure while deleting the old copy happens after the new copy is live, so the target is never half-deleted, and the installer names the hidden folder left behind. Windows cannot rename onto an existing directory, which is why the swap is two renames rather than one; an interruption between them leaves the target missing and the previous copy intact beside it. Every error is reported naming the targets already installed and the one that failed, without a traceback. A run deletes only the previous copy it moved aside itself; it never cleans up hidden folders from earlier runs, because no name can prove who made a folder (a user's `.okr-ninja.20260923.previous` backup looks like a leftover). An earlier run named any copy it left behind. A previous copy its owner cannot read or write is opened up to its owner before it is inspected for `.git` (mode restored if the install is refused) or moved aside, and the moved-aside copy is made fully accessible to its owner before deletion. Deletion retries only the calls that delete (`unlink`, `rmdir`): on POSIX it makes the containing folder writable, and only folders inside the old copy (judged against the outermost folder being deleted, so nested unlistable folders are handled too) — never a file's mode, so a file hard-linked from elsewhere keeps its permissions; on Windows it clears the read-only attribute of the path being deleted (git objects in a copied clone are read-only). A folder that cannot be listed is made listable and deleted whole; any other failure is re-raised, never retried. The source-conflict test compares file-system identity (`os.path.samefile`) between a real-directory target and the checkout and each of its parents — never path strings, which on macOS's case-insensitive default disk let `…/skills/OKR-Ninja` and `…/skills/okr-ninja` name one directory while comparing unequal. It runs only on real directories: a symlink target is always safe to unlink, which is what makes the old README's symlinked installs upgradable. A real-directory target holding `.git` is refused outright: it is a clone (the old README's `cp -R` copied `.git` along), not an installed copy, and may hold unpushed work.

**D7 — Home and project targets.** `<home>` is `Path.home()` (HOME on POSIX, USERPROFILE on Windows), which also lets tests point it at a temporary folder. `--project DIR` must name an existing directory, so a typo cannot scatter `.claude/` and `.agents/` folders into a new path; an empty value (an unset shell variable) is refused rather than read as "no project" or as the current folder.

**D8 — The shortened description.** Rules for the rewrite: lead with what it does and for whom ("Audits OKRs for one team or a whole portfolio…"); keep the two-mode claims, the from-scratch exclusion and the "trigger even without the word OKR" clause; keep representative single-team and portfolio example prompts and the verb "assess" (a competing single-team skill uses it, and a blind routing check lost an "assess" prompt without it); keep the closing sentence's trigger vocabulary but scope it to portfolio runs, since single-team runs produce no cross-team findings; no `: ` or ` #` (D2); target at most about 1,000 characters so a small later edit does not break uploads. The review-modes "repo is closed" requirement must still hold.

**D9 — Where the check runs.** In the verify gate's structural checks and in CLAUDE.md's testing step 1. Not inside `harness.py check`: the harness stays untouched, so this change needs no self-test cases.

## Risks / Trade-offs

- [The shortened description routes differently] → a fresh non-author subagent compares old and new descriptions against CLAUDE.md's three routing prompts during verify; the owner repeats the three prompts in Cowork after uploading.
- [Cursor lists the skill twice, reading both `~/.claude/skills` and `~/.agents/skills`] → README names `--only` for users who run only Cursor or only one other platform.
- [Uploaded copies go stale after a skill change] → README says to rebuild and re-upload; the plugin version bump marks shipped changes.
- [A stray untracked file under `references/` or `examples/` ships] → `build` lists every entry; verify compares with `git ls-files`.
- [The frontmatter reader refuses a valid but unusual YAML form] → it names the refused form, and the fix is to write the value as a plain or quoted single line.
- [The window between the two renames on replace] → an interruption there leaves the target missing but the previous copy intact beside it; re-running the installer restores the target, and the leftover is the user's to delete.
- [Hidden leftovers from failed or killed runs accumulate] → each is named when it is left; the installer never guesses which hidden folders are its own.

## Migration Plan

Nothing to migrate in the repo. Users who installed by hand re-run `python3 install.py`; a symlink from the old README becomes a copy, and the checkout it pointed at is left alone. Rollback is reverting the change: the skill folder layout is unchanged, so earlier manual installs keep working.
