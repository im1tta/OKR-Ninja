# Design — fix-fixture1-precision-extras

## Context

See `proposal.md` — Why. The design-relevant state:

- Four extras recur on fixture 1. The failing slice is `fixture1-portfolio` (3 counted, budget 2, one non-defect violation); `fixture1-platform-single-team` passes only because its single extra exactly fills a budget of 1.
- The eval criterion is absolute per key: **every** planted defect found in **every** run. That asymmetry drives most of the reasoning below — a key row is a promise the skill must keep every time, while an extra costs one unit of a small budget. Converting a flaky extra into a key row therefore makes the gate *worse*, not better.
- The catalog is partitioned across the two fixtures (`not_covered` in each key). AP-01 and AP-04 are fixture 1's; **AP-10 is fixture 2's**. Any AP-10 edit is a cross-fixture edit whether or not it intends to be.
- `CLAUDE.md` constrains the mechanics: rubric changes carry a before/after example with actual replacement text in the same file; keys are hand-edited as JSON and the fixtures' `## Answer key` sections are regenerated by `render-key --all`; AP/AL IDs are frozen.

## Goals / Non-Goals

**Goals**

- Each of the four extras is resolved at the altitude where the thing that is actually wrong lives, with the disposition recorded as a triage entry.
- The two rubric edits make a currently-undecidable boundary decidable, in a way a reader would want even if no fixture existed.
- Fixture 2's planted defects are provably untouched.

**Non-Goals (design level)**

- Not building any new grader capability. The harness already distinguishes non-defect violations, off-key findings and triage exclusions; nothing here needs a code change.
- Not attempting to drive extras to zero. The budget of 2 exists to absorb defensible judgment calls; the target is a fixture whose *recurring* extras are gone, not a fixture nobody can add a finding to.

## Decisions

### D1. Triage first, then one lever per extra

| Extra | Is the detection right? | Bucket | Lever |
|---|---|---|---|
| `AP-10 @ Objective PL1` | **No** — the objective names a change the rubric's own "with no delta" clause should have honored | `rubric-gap` | Sharpen AP-10; add a non-defect row |
| `AP-01 @ KR D2.1` | **Yes** — 100% rollout coverage is satisfied by a feature flag; non-defect N3 claims a property the text lacks | `fixture-ambiguous` | Reword D2.1; rewrite N3's rationale |
| `AP-01 @ KR D1.1` | **Yes** — an unplanted true defect | `fixture-ambiguous` | Reword D1.1; add a non-defect row |
| `AP-04 @ KR D2.2` | **Yes** — an unplanted true defect | `fixture-ambiguous` | Reword D2.2 to state its baseline |

Three of the four reports were **correct** and the fixture or its key was wrong. That is the finding that shapes this change, and it is the reason a single lever could not have worked: suppressing three correct detections in the rubric to make a fixture pass would have made the skill worse for every real user.

*Alternative rejected — plant the true defects as key rows.* D1.1 is caught in 1–2 runs of 5 and D2.2 in 1. A key row must be found in every run, so planting either converts a bounded precision cost into an unbounded recall failure. Rejected on the criterion's asymmetry, and recorded in the `eval-fixtures` delta so a future change does not re-propose it.

*Alternative rejected — a known-red triage entry per extra.* This is the "loosen the gate" move the verify gate names explicitly. It also requires user confirmation and is forbidden outright for the `skill-error` bucket. Every entry here lands as `fixed`.

### D2. AP-10 is tested on the objective statement, never on the KR set

The obvious sharpening — *fire AP-10 only when the objective's KRs carry no delta* — is wrong, and the fixture set proves it. Fixture 2's planted **G4** is Core Systems Objective CS1, "Continue running the platform smoothly for every team", whose KRs read `Sev-1 incidents per quarter 9 (Q4 actual, incident review) → ≤ 4` and `Cloud cost per completed delivery $0.42 → $0.30`. Both are real deltas with baselines. A KR-set test would have deleted fixture 2's only AP-10 defect while fixing fixture 1's extra — a silent recall regression traded for a precision win, in the exact blind spot the two-fixture partition exists to cover.

The two cases separate cleanly one level up:

| | Objective statement | Names a change? | AP-10 |
|---|---|---|---|
| Fixture 1 PL1 | "Keep the lights on, **cheaper**" | Yes — realized by PL1.2, `$4.10 → $3.20` | Does not fire |
| Fixture 2 CS1 | "Continue running the platform smoothly for every team" | No | Fires |

So the rule is a two-part test on the objective: it names a change, **and** at least one KR realizes that named change with a baseline→target pair. The second half is what stops "Keep the lights on, better" from dodging the anti-pattern by adjective. AP-10 remains an anti-pattern about the objective — which is what its definition already says ("Routine operational duty presented as a goal") — and the KRs enter only as the evidence that the named change is real.

### D3. AP-01 gains a rescue clause, not a new trigger

AP-01's detect line is `KR begins with ship/launch/implement/migrate/complete/build/write; no metric, no baseline→target pair`. Applied to "Ship personalized onboarding checklists to 100% of new signups" it is genuinely undecidable: there *is* a number, and whether "100% of new signups" is a metric is exactly the question. Hence the same surface shape gets opposite verdicts on D2.1 and D1.1, and the skill cannot converge.

The clause added is an **exclusion only**: a delivery-verb KR is not AP-01 when it states a result measure that shipping alone does not satisfy; a coverage or completion percentage of the team's own delivery is not such a measure. **This first formulation was wrong and did not ship — see D3a.** It is kept here as the decision it was, because the repair only makes sense against it.

Two safety properties were checked against the existing fixture, because a widened AP-01 would manufacture new extras:

- **The trigger list is untouched.** `Close 100% of pen-test findings rated High or above (currently 7 open)` (PL2.1) is completion of the team's own work with a coverage denominator — materially the same shape as D1.1 — and is silent today because "Close" is not a trigger verb. An exclusion-only clause keeps it silent. Widening the trigger to "any completion verb" would have created a fifth recurring extra while fixing four.
- **Baselines stay AP-04's business.** Requiring the rescuing measure to carry a baseline→target pair would have pulled non-defect **N2** (Growth G1.3, "Launch self-serve plan upgrades by Aug 15 and drive 300 upgrades through the new flow this quarter") into AP-01 — 300 upgrades is an adoption count with no baseline. The clause therefore rescues on the *kind* of measure, and leaves a missing baseline to AP-04 under Part 5's existing precedence.

### D3a. Repair cycle 1 — the first AP-01 clause was a cross-fixture regression

The clause as first written said a coverage or completion percentage of the team's **own** delivery never rescues. The acceptance batch measured what that costs: `fixture2-portfolio` fell to 1 of 5 passing, with `AP-01@KR AC4.2` firing in 4 runs — a direct violation of fixture 2's intentional non-defect **N7**, which records "Billing-system migration covering 38% → 100% of the 6,400 self-serve accounts" as *not* AP-01 ("bounded completion of an in-flight migration with a countable coverage denominator") — plus `AP-01@KR CR3.1` ("0/14 → 14/14") in 4 runs on the same reasoning.

D3's safety analysis checked fixture 1's non-defects and never checked fixture 2's. That is the same cross-fixture blind spot D2 was written to avoid for AP-10, walked into one section later. Run cost rules out thoroughness as the explanation: 176k tokens and 1059s mean against the prior batch's 183k and 1002s.

The second attempt — rescue only on a baseline→target pair — was rejected before it was measured, because it would have broken fixture 1's **N2** ("drive 300 upgrades through the new flow", an outside-moved measure with no baseline). The two fixtures pull in opposite directions, so the discriminator is a **disjunction**, which is what AP-01's trigger already implied: a delivery-verb KR fires only when it has *neither* an outside-moved result measure *nor* a baseline→target pair.

| Case | Outside-moved measure | Baseline→target | Verdict |
|---|---|---|---|
| fx1 G1 · P1.2 "Ship checkout & billing API v2 to GA by Sep 26" | no | no | **fires** (planted) |
| fx1 N2 · G1.3 "drive 300 upgrades through the new flow" | yes | no | silent |
| fx2 N7 · AC4.2 "billing migration 38% → 100% of 6,400 accounts" | no | yes | silent |
| fx2 · CR3.1 "0/14 → 14/14 flows instrumented" | no | yes | silent |
| old D2.1 "Ship … to 100% of new signups" | no | no | **fires** — the original complaint |

The lesson generalizes past this change and is written into the `goodness-findings` delta as a scenario: a detect-rule edit is checked against **every** fixture's non-defects, not only the one whose extras motivated it.

### D4. Concrete fixture replacements

Proposed text, to be confirmed against the anti-pattern sweep during apply:

| KR | Now | After |
|---|---|---|
| D1.1 | Migrate 100% of product events to unified event schema v2. | Cut cross-source metric discrepancies flagged by the weekly exec-dashboard reconciliation check from 14 to 0, by serving all product events from unified event schema v2. |
| D2.1 | Ship personalized onboarding checklists to 100% of new signups. | Ship personalized onboarding checklists and cut new-signup support tickets in the first 7 days from 38 per 100 signups to 20. *(revised during apply — see D4a)* |
| D2.2 | Lift new-user activation rate to 35% via onboarding experiments. | Lift new-user activation rate from 31% to 35% via onboarding experiments. |

Each replacement was chosen against three constraints at once:

- **Dependent rows survive.** D1.1 keeps the schema-v2 migration as its stated mechanism, so row **A2** (AL-01) still has a migration for the Data notes' "rides on the streaming pipeline migration" to ride on. D2.2 keeps 35% and adds the same 31% Growth states, so row **A4** (AL-03, with AL-02 accepted) gets *sharper*: same metric, same baseline, incompatible targets.
- **No new anti-pattern is introduced.** D1.1 names its instrument ("the weekly exec-dashboard reconciliation check") so it does not read as AP-09 the way D1.3 deliberately does; D2.1 states its denominator ("per 100 signups") against AP-13 and carries no date, so it does not duplicate N2's AP-14 near-miss.
- **The near-miss is preserved.** D2.1 keeps "Ship" as its opening verb. That is the whole point of N3: a KR that *looks* like AP-01 and correctly is not. Rewriting it into something unmistakably fine would retire a false-positive probe instead of fixing it.

### D4a. Why D2.1's replacement is a support-ticket rate, not an adoption rate

D4 first proposed measuring "the share of new signups completing at least three checklist steps". Writing it out
exposed a realism problem the table hid: the checklists ship *this* quarter, so any completion baseline is either
0% — inviting an AP-07 reading of the ratio and stating no real starting point — or a number the fixture cannot
justify. A support-ticket rate has a genuine pre-existing baseline (38 per 100 signups), an explicit denominator,
and is still moved by what signups experience rather than by the team shipping, which is the property the rescue
clause and non-defect N3 actually turn on.

The substantive requirement is therefore "a measure shipping alone does not satisfy", not "an adoption measure";
the `eval-fixtures` delta says so, since that text is what archive syncs into the main spec. Recorded here because
an implementation that quietly departs from its own design table is the failure this repo's change-of-record
exists to prevent — the refute-mode verify pass caught it, which is what that pass is for.

### D5. Two new intentional non-defects, so the anchors are guarded

- **N7** — forbids `AP-10` at Objective PL1. Without it, an AP-10 anchor that regresses is absorbed by the budget instead of failing loudly.
- **N8** — forbids `AP-01` at the reworded KR D1.1, which still opens on a delivery flavor and is the case the rescue clause exists to decide.

A non-defect row is a claim the change has to be right about, so each is stated only where the reasoning above is explicit. N3 is rewritten rather than deleted: its purpose was always sound, only its text was not.

### D5a. Repair cycle 2 — fixture 2's own unplanted defect, and the one deliberately left

With the AP-01 clause repaired, `fixture2-portfolio` reached 4/5. Three extras remained, and they are not one problem:

- **`AP-12@KR AC3.2` ×3 — fixed.** "Partner portal live for the first 40 partner accounts, 0 → 40" carried no causal chain to its objective, "Customers trust the delivery promises we report". The reading is defensible, the key never planted it, and it meets the recurring bar — the same unplanted-true-defect class as fixture 1's D1.1 and D2.2, one fixture over. The KR now names the delivery reporting it gives those partners. The reword preserves everything the key leans on: the portal itself and its stretch/billing-migration gating are load-bearing for row **A5** (AL-12 commitment asymmetry, against Dispatch's committed DS2.2) and for non-defect **N4** (AP-07 does not fire on a gated, explicitly-stretch zero-baseline launch).
- **`AL-05@Objective CR2` ×2 — analysed, deliberately left.** The detection is also defensible: CR2 declares *(supports C3)*, C3's metric is driver-app weekly **retention**, and CR2's only KR measures referral **installs** — acquisition, which does not move a retention rate. The available fixes are all worse than the symptom. Naming the missing link ("referred drivers retain better") puts a mechanism on the Courier page, and planted defect **G2** (AP-07 Unmoored Moonshot on the 15x CR2.1) requires that the page state no mechanism — the fix would delete a planted defect to remove an in-budget extra. Re-pointing CR2 at another priority is worse: no company priority C1–C4 is moved by referral installs. Planting it as a key row is barred by the same recall asymmetry as everywhere else in this change (2 runs of 5). At ×2 against a budget of 2 it is exactly what the budget exists to absorb.
- **`AL-10@KR DS2.2` ×1 — left.** One run of five is not a recurring extra by any threshold this repo uses.

This is the boundary of "fix the thing that is actually wrong": AC3.2 was wrong, CR2's tension is real but every available lever costs more than it buys, and saying so in writing is better than a silent tolerance.

## Risks / Trade-offs

- **[The AP-01 clause suppresses true detections on real OKRs]** → The clause is an exclusion whose scope is one sentence and whose worked example shows a KR that still fires. The candidate tier's per-row recall counts are the guard: G1 (AP-01 on P1.2, "Ship checkout & billing API v2 to GA by Sep 26" — no measure at all) must keep its hit rate, and a drop there is the signal the clause overreached.
- **[The AP-10 edit breaks fixture 2's G4]** → Directly mitigated by D2's objective-statement test, and measured: `fixture2-portfolio` runs in every tier of the acceptance batch specifically as the control for this.
- **[Three fixture rewordings break a dependent answer-key row in a way reading cannot catch]** → `harness.py check` fails on any unresolved evidence anchor, and the acceptance batch grades A2 and A4 directly. Both rows are named in tasks as explicit verification points rather than left to the batch verdict.
- **[The committed batches stop being a valid baseline for fixture 1]** → Accepted, and stated in the proposal's Non-goals. `compare --baseline-batch` against a pre-change fixture-1 batch is apples-to-oranges after this lands; the acceptance test is therefore the *absolute* criterion, which the repo owner has already established (2026-09-09) as the standing bar. Fixture 2's batches remain comparable.
- **[The reworded KRs make fixture 1 easier overall, flattering the next measurement]** → Partly true and worth naming: three sloppy KRs become clean ones. The planted defects are untouched, the two new non-defect rows add two *new* ways to fail, and the near-miss character of D2.1 is deliberately preserved, so the fixture's false-positive pressure is redistributed rather than removed.

## Migration Plan

Not applicable — no schema, no stored data, no consumer contract. The change is text in five files plus a regenerated answer-key section. Rollback is `git revert`; the eval keys and the fixtures move together in one commit so no intermediate state has a key that disagrees with its fixture.

## Open Questions

None that would change the specs, the approach, or the task breakdown. The exact wording of the three replacement KRs is settled in D4 and may be adjusted during apply only if the anti-pattern sweep in task 2.4 shows a replacement introduces a defect of its own — a possibility the tasks already carry a step for.
