## Context

See proposal.md — Why. The orchestrating session launches each run as a background Agent; the launch result names an `output_file` (`<session tasks dir>/<agentId>.output`), a JSONL transcript with one object per line. Verified on the 2026-09-14 transcripts:

- Assistant lines have `message.role == "assistant"`, `message.id`, `message.model` (`claude-sonnet-5`, `claude-opus-5`), `message.usage` (`input_tokens`, `output_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens`) and `message.content` as a list of `text`, `thinking` or `tool_use` items. One API message is spread over several lines that share `message.id`; the usage on each line is the running figure for that message, so the last line per id carries its final usage.
- Tool results are `tool_result` items (with `is_error`) inside user-role lines. There are also `type: "attachment"` lines and a leading user line with the prompt; every line carries `timestamp`.
- The runner's final reply is the text of the last assistant message that has text items. Extracting it with `json.loads` and comparing to `returned-message.txt` (23 068 bytes, em-dashes and all) matches byte for byte. The completion notification, by contrast, HTML-escapes `<` and `&`.

Constraints: stdlib only; the grader's quote rules are untouched; committed batches must grade and aggregate unchanged; no evasion of the Write guard.

## Goals / Non-Goals

**Goals:**
- Reports reach `report.md` byte-exact from the transcript, never from a notification and never re-typed by the runner.
- A failed capture is a named, visible outcome, not a "runner did not finish".
- Every existing subcommand keeps its behaviour on batches that predate this change.

**Non-Goals:**
- A headless driver (option C), multi-model batches, in-batch retries, changes to grading rules.

## Decisions

**D1 — A new `capture` subcommand, not an extension of `record`.** `record` is a pure provenance writer with no failure modes: it merges whatever flags it is given into `run.json` and exits 0. Capture has to read a transcript, decide whether a report exists, write or refuse to write `report.md`, and fail loudly on a model mismatch. Folding that into `record` would give one command two contracts and make every committed batch's `record` semantics ambiguous. `record` stays as it is (still usable to patch tokens or seconds afterwards); `capture` writes the same `run.json` keys plus the new ones, so `grade_run_dir` reads one shape. Alternative rejected: `record --transcript`, for the reason above.

**D2 — Marker format.** Two exact lines, each on its own line, each required exactly once, begin before end:

```
=====BEGIN OKR-NINJA REPORT=====
=====END OKR-NINJA REPORT=====
```

Chosen because the strings cannot occur in a compliant report (no markdown meaning, no heading form the grader parses, not a fixture phrase), they survive any renderer as plain text, and "exactly once each" is checkable by counting lines. A marker line matches exactly — no surrounding whitespace or tabs — with one tolerance: a trailing carriage return, so a CRLF transport still validates (carriage returns inside the body are preserved as bytes). The report is the text strictly between the begin line's newline and the end line, kept exactly as emitted (blank lines before the end marker included); capture adds a final newline only when the body lacks one, matching how every committed `report.md` ends. A block whose body is empty or only whitespace (spaces, tabs, CR, LF) is `empty-report`, not a one- or two-byte report; a body with any other character is never stripped. A code fence is explicitly forbidden in the prompt because a fence would become part of the report and break the heading-based finding parser.

*Final message = API message, not JSONL line.* One API message is spread over several JSONL lines sharing `message.id` (in the acceptance transcripts every line carries exactly one content item, so a thinking line and a text line of the same reply are separate lines). The parser groups assistant lines by unique id in first-appearance order — not by runs of consecutive lines, so ids interleaved as m1, m2, m1 still form two messages (a line without an id is a message of its own); the final message is, among ids carrying any text item, the one whose last transcript line is latest, and its text items are concatenated in order with nothing inserted between them, so the result holds only bytes the runner emitted. Taking the last text-bearing *line* instead would split a reply whose text arrives on two lines and report `markers-missing`.

**D3 — Not-produced reason names.** `run.json` gains `not_produced` with one of: `agent-error` (the orchestrator passed `--agent-error`, or the transcript has no assistant turn), `transcript-unreadable` (a file that cannot be read for any OS reason, a line that is not JSON, report text that is not encodable as UTF-8, or a line whose relied-on fields — `timestamp`, `message.id`, `message.model`, `message.usage`, `message.content` — have an unexpected shape), `no-final-text` (assistant turns exist but none carries text), `markers-missing` (final text has no complete block), `multiple-blocks` (more than one begin or end line), `empty-report` (a marker block with no report text), `model-mismatch` (`--model` disagrees with the transcript, including a transcript that records no model at all). The first three are transport failures and the last three are runner-format failures; the grade's `failures` list reads `report not produced: <reason>` and the scorecard's per-slice `not_produced` map counts each reason. A run with no `run.json` reason (every committed batch) keeps the exact legacy string `report not produced`, so re-grading old batches changes no committed figure. Precedence, in the order the code checks: `--agent-error` wins over everything (a transcript problem found alongside it is appended to `not_produced_detail`); then `transcript-unreadable`; then `agent-error` for a transcript with no assistant turn; then `model-mismatch` (checked before the reply is examined, as the spec's model scenario requires); then `no-final-text`, `markers-missing` / `multiple-blocks`, `empty-report`; and last an unencodable body, reported as `transcript-unreadable`. Capture never crashes on a transcript: it parses before touching the run directory, every shape error is a named reason, and `run.json` is written on every path. The catch-all for errors the parser did not anticipate (a `RecursionError` from pathologically nested JSON, an `OverflowError` from a usage value like `1e400`) yields exactly the provenance shape of the other unreadable paths — `model: null`, `models_seen: []`, `transcript_usage: null`, `tokens`/`wall_seconds` from the command line or null, a fresh `started_at` — with the same `--agent-error` precedence and detail. The record is then serialized to its exact bytes in memory before anything is written; if that fails (a lone surrogate in a timestamp, model, transcript path or command-line text; an unrepresentable number), the record is replaced by a **fallback record** that cannot fail: reason `transcript-unreadable` — or `agent-error` when `--agent-error` was given, its text escaped — with an ASCII-safe detail naming the serialization failure, `model: null`, `models_seen: []`, `transcript_usage: null`, `tokens`/`wall_seconds` from the command line only when they serialize (else null), a fresh `started_at`, the stale-removal flags, and every string made ASCII-safe by backslash escaping; it is serialized with `ensure_ascii`. No report is produced from a fallback. Every capture run.json carries exactly the same key set (`RUN_JSON_KEYS`), which the self-tests assert. A run whose `run.json` carries no reason — a legacy run recorded before capture existed, or a run capture never wrote because the command exited on a usage error (a non-integer `--tokens`) — is counted under `unknown` in the scorecard's per-slice map.

**D4 — Model from the transcript, `--model` as a cross-check.** The recorded model is the model of the final assistant message as D2 defines it (the text-carrying id whose last line is latest — so interleaved ids m1(A), m2(B), m1(A) record A); when that message records no model, or no message carries text, the latest model seen. The set of models seen across messages is recorded as `models_seen`. A `--model` that differs from the recorded model — or is given when the transcript records none — fails with exit 1, no `report.md`, and reason `model-mismatch` (the spec says a disagreeing orchestrator model is rejected, never recorded; a model-less transcript cannot confirm it). An unreadable transcript records `model: null` rather than carrying an older `run.json` value forward — on every path, including the catch-all, because provenance is built from the transcript and the command line only (see D6). The orchestrator therefore no longer needs to know its own model id to record provenance, which is what the `record --model` step relied on. Batches stay single-model: `aggregate` keeps its mixed-model warning and `compare` keeps refusing mismatched models.

**D5 — Tokens and seconds.** `--tokens` and `--seconds` from the Agent usage line take precedence when given, because that is the figure every committed `run.json` carries and the scorecard's cost columns compare like with like. Capture also records `transcript_usage` (per-message final usage — the last line seen for each unique `message.id` — summed over unique ids: input, output, cache-creation and cache-read tokens, plus message count) and derives `started_at` from the first line's timestamp and a fallback `wall_seconds` from first-to-last timestamps when `--seconds` is absent; when `--tokens` is absent, `tokens` falls back to the transcript's input + output + cache-creation + cache-read total.

**D6 — Pre-existing `report.md` and `grade.json` are replaced.** The transcript is the sole source of truth. If a runner disobeyed and wrote a file (for instance via Bash), or an earlier capture attempt was graded, capture removes `report.md` and `grade.json` from the run directory whenever it runs — after parsing, so a crash-free decision is already in hand — records `stale_report_removed` / `stale_grade_removed`, and writes the captured report only when validation succeeds. Otherwise a disobedient run could be graded from a re-typed file, which is the defect this change removes, and a batch aggregated after a failed capture then resumed would keep the old not-produced grade because `aggregate` grades only runs lacking `grade.json`. `run.json` is likewise rebuilt from scratch: **no field of an earlier `run.json` survives a capture**, whatever its content or the outcome — the new record holds only the transcript path, the flags (`previous_run_json_replaced`, `stale_report_removed`, `stale_grade_removed`), the provenance built from the transcript and the command line, and the not-produced reason and detail. A `record` invocation after capture can still add tokens or seconds on top.

*Write ordering.* Capture touches the run directory only after the decision is made and the exact bytes of `run.json` (and of `report.md`, when produced) exist in memory: (1) stage them as `run.json.tmp` / `report.md.tmp` in the run directory — `*.tmp` is gitignored, never graded, and not what `plan` looks for; (2) remove the stale `report.md` and `grade.json`; (3) `os.replace` the staged files into place. A write failure before step 2 (a read-only directory, a full disk) removes the staged files, prints the error to stderr, exits non-zero, and leaves the directory exactly as it was — stale files are never deleted without a valid `run.json` ready to replace them, and an interrupted write can never leave a 0-byte or partial `run.json`. A failure during steps 2–3 — an immutable stale file, a `run.json` that is a directory — can leave stale files already removed with the old `run.json` still in place (or, after step 3's first move, the new `run.json` in place without its `report.md`); capture then exits non-zero with a message naming exactly which stale files were removed and whether `run.json` was written, and asks for `capture` to be re-run on the same transcript. Until it is, `plan` lists the run as pending, because no `report.md` exists. The whole command body is wrapped so no exception escapes as a traceback.

**D7 — Prompt-hash mismatch in `compare` warns, it does not refuse.** The regression rule measures skill content between arms; the prompt template is transport. This very change alters the hashes, and a refusal would make every comparison against a pre-change baseline batch impossible while the model refusal already protects the scorer. The warning names each mode whose hash differs, is printed, and is recorded in `comparison.json` under `warnings` plus a `prompt_hashes` entry per arm. Model mismatch stays a refusal (exit 2) because a different model changes the thing being measured.

**D8 — `HARNESS_VERSION` 2 → 3.** The run transport, the `run.json` shape, the grade's failure string for not-produced runs, and the scorecard schema all change. Nothing checks the version for equality, so old batches still load; the number exists so a reader of a batch can tell which transport produced it.

**D9 — Self-tests as synthetic JSONL.** Real transcripts hold system prompts and environment details and are not copied into the repo. Each capture case is a small hand-built JSONL mirroring the observed shape (a user line, assistant lines with `id`, `model`, `usage`, `content` items, a `tool_result` line with `is_error`, an `attachment` line, timestamps). The selftest runner gains a `type: "capture"` case that runs capture into a temporary directory and checks `produced`, the reason, the recorded model, and byte-equality of `report.md` against an `expected.md`.

**D10 — Orchestrator contract.** `/okr-eval` step 2 becomes: launch the Agent with the prompt verbatim, wait for completion, then run `capture <run_dir> --transcript <output_file> --tokens N --seconds S` (model omitted, or passed only as a cross-check). The orchestrator never reads report text from the notification, never edits or writes `report.md`, and never relaunches a run in the same batch; failed captures are reported by reason and resumed later with `--batch`.

## Risks / Trade-offs

- [The environment changes the transcript format again] → the parser only depends on `message.role`, `message.content[*].type/text`, `message.model`, `message.id`, `message.usage` and `timestamp`; every other line type is ignored, and an unparseable file is a named reason rather than a crash.
- [A runner puts the report between the markers but adds a code fence] → the prompt forbids it explicitly; if it happens the grader's structure check fails visibly (no headings parsed), which is the correct verdict for a non-conforming reply.
- [A runner emits the markers twice, once in a draft] → `multiple-blocks`, no report, visible in the scorecard; not retried, by decision.
- [Multiple `text` items concatenated differ from how the notification rendered them] → the notification is never the source; concatenation inserts no bytes, and the concatenated text is what is graded.
- [Committed batches re-aggregated under version 3 would rewrite their `scorecard.json`] → `aggregate` re-grades only runs lacking `grade.json`, and the verification step restores `evals/runs` with `git checkout` afterwards.

- [Model-id format differs between transports] → committed batches from 2026-09-10 on (`2026-09-10-candidate-5beed03`, `2026-09-10-candidate-repair1`, `2026-09-10-candidate-repair2`, `2026-09-10-smoke-9551238`, `2026-09-10-smoke-verify`, `2026-09-11-candidate-cbdeba3`, `2026-09-11-smoke-cbdeba3`) record the orchestrator's session identity `claude-opus-5[1m]`, while `capture` records the transcript's `claude-opus-5`. `compare <new batch> --baseline-batch 2026-09-11-candidate-cbdeba3` therefore exits 2 with "arms ran on different models". This is deliberate: the model check is neither normalised nor relaxed here (owner's explicit wish), so a cross-transport comparison needs a fresh baseline batch captured under the new transport. Whether the `[1m]` suffix should be treated as the same model is an owner decision, pending.

## Migration Plan

No data migration. Old batches keep grading; new batches use the new prompts and `capture`. Rollback is reverting the change; batches captured meanwhile remain gradable because their `report.md` is an ordinary file.
