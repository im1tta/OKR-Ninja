# Coppervale — Q1 2027 OKR portfolio review

*Scope: 5 teams (Dispatch, Courier, Core Systems, Insights, Accounts) · Period: Q1 2027 · Mode: portfolio · Source: `sample-portfolio-2.md` (company priorities page 91050, five team OKR pages, Q4 2026 business-review appendix) · Strategy source in scope: "Company Q1 2027 priorities" (C1–C4).*

## 1. Executive summary

**Verdict: At risk.** 5 teams reviewed; 2 Critical, 10 Major, 1 Minor findings.
The portfolio's biggest threat is **AL-11 Circular dependency**: Courier's instrumentation waits on Core Systems' SDK GA, Core Systems' GA waits on Insights' schema validation, and Insights' validation waits on Courier's instrumentation — a closed three-team cycle with no valid execution order, and every edge is stated as a hard block in the teams' own notes.
No goodness anti-pattern repeats across teams — each of the seven goodness findings is a distinct catalog entry — and the most consequential is **AP-13 Ambiguous Denominator** (Dispatch's "failure rate" KR, which can never be scored the same way twice).
Two teams also carry incompatible definitions of one company-visible metric (AL-08 Terminology collision on the on-time delivery rate metric), and the only company priority dated to this quarter — C1's $14M → $17.5M ARR run-rate — is carried by no team's KR at all (AL-10 Strategy coverage gap).
Recommended first action: Core Systems convenes Courier and Insights in week 1 to cut one edge of the telemetry cycle before any of the three teams plans against it.

### [Critical] AL-11 Circular dependency: Courier ↔ Core Systems ↔ Insights
- Courier evidence: "Instrument all 14 core driver flows with telemetry SDK v1 (0/14 → 14/14, flow coverage checklist) once Core Systems GAs the SDK." (`sample-portfolio-2.md` › Objective CR3: Every driver action is visible to the teams that need it › line 46)
- Core Systems evidence: "GA telemetry SDK v1 after Insights validates event schema v3 in production, with internal apps live on it 1 → 3 (SDK adoption dashboard)." (`sample-portfolio-2.md` › Objective CS3: One telemetry pipeline every product team trusts › line 67)
- Insights evidence: "Validate event schema v3 in production — 22 of 22 v3 event types passing conformance checks (0/22 → 22/22, schema CI suite) — after Courier instruments the new driver-app event stream. Owner: Halima D." (`sample-portfolio-2.md` › Objective IN2: Every product event lands in one trusted schema › line 84)
- Conflict: Courier waits on Core Systems' GA, Core Systems waits on Insights' validation, and Insights waits on Courier's instrumentation — a closed three-team cycle with no valid execution order as written. Nothing starts, and all three KRs fail together, taking with them the C4 pipeline-consolidation work that each of the three objectives claims to serve.
- Detection check that fired: AL-11 structural cycle detection on the dependency map — three quotable blocking edges (Courier→Core Systems, Core Systems→Insights, Insights→Courier) closing into a cycle.
- Disconfirming checks run: **hard block vs soft preference** — each edge uses unhedged sequencing wording ("once", "after", "after"), and each team's own notes restate the block as settled fact ("SDK timing per Core Systems' plan." line 49; "SDK v1 is code-complete; GA is gated on schema v3 validation (Insights)." line 70; "schema v3 validation is sequenced behind Courier's instrumentation of the new event stream; the conformance suite is ready." line 87) — no edge is soft, so no downgrade. **Staged-milestone interleaving** — checked; Courier's edge names GA specifically rather than a beta or pre-release channel, and no page offers a pre-GA path, so the milestones cannot be interleaved into a valid order. **Awareness plus resolution plan** — all three notes sections searched; none mentions the other two edges together and none proposes a sequence, so the Minor downgrade does not apply. **Commitment level** — Core Systems' and Insights' KRs are committed under their pages' stated convention (lines 55 and 76) and neither is marked stretch; Courier's page states no convention at all, but per the taxonomy a team that labels nothing has not implicitly marked everything aspirational, and CR3.1's wording is a hard block — so all three edges read as committed and the finding stays Critical.
- Inference labels: none — all three edges are quoted verbatim; no link in the cycle is inferred.
- Verdict: CONFIRMED (all three quotes re-verified character-for-character against the source file)
- Recommended resolution owner: Core Systems lead (Adaeze O.) convenes Courier (Tomás R.) and Insights (Halima D.) in week 1 to cut exactly one edge — the cheapest cut is a pre-GA SDK channel that lets Courier instrument the driver-app event stream before GA — then all three KRs are re-dated against the agreed sequence.

### [Major] AL-08 Terminology collision: Dispatch ↔ Accounts
- Dispatch evidence: "On-time delivery rate — jobs completed within the promised window as a share of all completed jobs, measured weekly in the Ops Console — 91% → 95%." (`sample-portfolio-2.md` › Objective DS2: Enterprise teams run their whole day in Coppervale dispatch › line 26)

(`sample-portfolio-2.md` › Objective AC3 (Priority: P0): Customers trust the delivery promises we report › line 104)
- Conflict: one metric name, two incompatible measurements — different numerator event (job completion vs destination scan), different denominator (completed jobs vs all scheduled deliveries including cancellations), different window (weekly vs monthly) and different system of record (Ops Console vs Billing warehouse). Both teams carry committed targets on the on-time delivery rate metric and the company priority C2 names "keeping the delivery promises we report to customers" (line 11), so any exec rollup of this metric returns two different truths (91% → 95% and 78% → 85%) and neither team is accountable for the other's number. Secondary ID cross-referenced: AL-03 Duplicated / overlapping objectives — two teams hold a target on the same named metric with no stated division of labour — reported here because the terminology collision is the root cause that hides the overlap.
- Detection check that fired: AL-08 form (a), same name / different definition — blocking on every metric name used by two or more teams, then diffing each team's stated formula, window, population and data source.
- Disconfirming checks run: **different wording ≠ different definition** — both definitions normalized to (numerator event, denominator population, window, data source) and they differ on all four axes, so the collision is substantive, not cosmetic. **Superseded or shared glossary** — both team pages and the company priorities page searched for one shared definition of the on-time delivery rate metric; none exists, and the only definitional statement is Dispatch's own "On-time delivery is measured per our Ops Console methodology (see KR DS2.1)." (line 31), which asserts Dispatch's reading without acknowledging that Accounts uses another. **Page versions** — Dispatch last updated 2027-01-04, Accounts 2027-01-08; neither page supersedes the other and neither records a revision.
- Inference labels: none — both definitions are quoted verbatim from the teams' own KR text.
- Verdict: CONFIRMED
- Recommended resolution owner: CEO (Noor E.) as C2's owner, with Dispatch (Mei L.) and Accounts (Georg B.): agree one company definition and one system of record for on-time delivery before mid-quarter, then re-baseline whichever team's target moves; until then, rename the losing metric so the two numbers can never be rolled up as one.
