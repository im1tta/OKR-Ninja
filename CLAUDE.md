# CLAUDE.md — for agents developing this repo

This repo is an Agent Skill ("okr-ninja") that audits OKRs for quality ("goodness") and cross-team alignment in two modes selected by team count at scope intake: **portfolio mode** (2+ teams — breadth and alignment) and **single-team mode** (one team — full-depth goodness review). The skill is closed and self-contained: it never defers OKR review to any external skill.

## File map and ownership (no duplication between files)

| File | Owns | Must NOT contain |
|---|---|---|
| `SKILL.md` | Trigger description (frontmatter) + the step-by-step review procedure, pointers to references | Rubric dimension definitions, alignment failure-mode definitions, output templates, severity definitions |
| `references/goodness-rubric.md` | The ONLY home of rubric dimensions (O1–O4, K1–K7), 0–4 scoring anchors, team-dimension aggregation and roll-up rules, and the AP-XX anti-pattern catalog | Alignment content, report/finding templates, severity-scale definitions |
| `references/alignment-taxonomy.md` | The ONLY home of AL-XX cross-team failure modes and their detection heuristics | Goodness/rubric content, report/finding templates, severity-scale definitions |
| `references/report-format.md` | The ONLY home of output/finding templates, the Critical/Major/Minor severity scale, and the source-ref format | Rubric or taxonomy definitions (it references them by ID and canonical name only) |
| `examples/sample-portfolio.md`, `examples/sample-portfolio-2.md` | Test fixtures: fictional company priorities + team portfolios with planted defects (fixture 1: Brightledger, 4 teams; fixture 2: Coppervale, 5 teams, covering the catalog modes fixture 1 leaves uncovered); each file's `## Answer key` section (planted defects, intentional non-defects, triage entries, eval criterion, slices) is **generated** from its JSON key under `evals/keys/` | Real company data; hand edits below the `## Answer key` heading (edit the JSON key, then `python3 evals/grader/harness.py render-key --all`) |
| `evals/` | The eval harness: `evals/keys/*.json` — the ONLY hand-edited source of each fixture's answer key (accepted IDs, evidence anchors, non-defects, not-covered lists, budgets, slices, triage entries); `evals/lifecycle/scenarios.json` — the ONLY hand-edited source of the artifact-lifecycle eval (deliverable keys, seeded registry and seam state, cycle dates, expected outcome per key, summary markers), beside `evals/lifecycle/publish_seam.py`, the local stand-in for the artifact surface; `evals/corpora/` — scratch **non-fixture** review corpora, which the publish contract's file test classifies as publishable, so a lifecycle run publishes as a user's own export would; `evals/prompts/` — frozen run-prompt templates; `evals/grader/harness.py` — the deterministic, stdlib-only grader (`check`, `render-key`, `plan`, `capture` — writes a run's `report.md` byte-exact from the subagent transcript's marker block, since runners return the report as their final message rather than writing it — `record`, `grade`, `aggregate`, `compare`, `lifecycle-plan`, `lifecycle-grade`, `selftest`) with its self-test corpus under `evals/grader/selftest/`; `evals/runs/<batch>/` — committed batches (prompt, report, run.json, grade.json per run; scorecard.json, comparison.json per batch; a lifecycle batch commits prompt, summary, `work/`, `seam/store.json` and grade per scenario) | Skill content; rubric, taxonomy, or report-format definitions; planted catalog defects or answer keys in a corpus under `evals/corpora/` (those belong to the fixtures under `examples/`) |
| `README.md` | Human-facing overview, install, usage, and the ONLY home of the product context: reader personas per mode, the target use-case (cross-cycle drift tracking) vs. what is built today, the four-job priority order that breaks depth-vs-brevity ties, and the distribution intent | Procedure details agents follow |
| `install.py` + `dist/` | `install.py` — the stdlib-only installer, package builder and frontmatter check (`install` copies the skill into `.claude/skills/` and `.agents/skills/`; `build` writes `okr-ninja.skill` and `okr-ninja.plugin`; `check` applies the skill-upload rules plus the `metadata.version` rule). It reads the checkout it sits in or, in remote mode (every other case: piped, a copy downloaded on its own, or any of `--release`/`--repo`/`--source`; see its docstring), a published GitHub Release (the latest, or the `--release` tag) or a local `--source` zip, read from the archive in memory. It is the ONLY definition of what ships: the runtime payload `SKILL.md` + `LICENSE` + `references/` + `examples/`. `dist/` is checkout build output, git-ignored and never committed | Skill content; human install instructions (README owns them); any file from outside the runtime payload in an install or package |
| `LICENSE` | The MIT license, which ships inside every installed copy and package. The skill's version lives only in `SKILL.md`'s frontmatter `metadata.version`, which `build` copies into the plugin manifest | Any other license or version text |
| `tests/` | `tests/test_install.py` — the offline, stdlib `unittest` suite for `install.py`: remote-mode detection, archive reading and refusals, redirect and host pinning through a fake HTTPS handler, version and tag agreement, and end-to-end install, update and build into scratch folders | Skill content; eval fixtures or keys (those belong to `examples/` and `evals/`) |
| `openspec/` + `.claude/` | OPSX change-of-record scaffold, commands, and skills (see Change workflow below); `.claude/commands/okr-eval.md` — the `/okr-eval` command that runs eval batches through subagents on the subscription and grades them with the harness | Skill content |

If a rubric dimension needs explaining, it goes in `references/goodness-rubric.md` and everywhere else refers to it by name. Same rule for failure modes (`references/alignment-taxonomy.md`), and for templates, severities, and source-ref formats (`references/report-format.md`).

## Editing rules

- **Keep `SKILL.md` under ~150 lines.** If an edit pushes it past that, move detail into the appropriate `references/` file instead.
- **Every rubric or taxonomy change needs a matching example in the same file.** For a goodness anti-pattern: a bad OKR (before) and its concretely rewritten form (after) — actual replacement text, not advice about writing one. For an alignment failure mode: a scenario narrative plus the detection heuristic that catches it may stand in for an after-state. A new anti-pattern or failure mode without its example does not merge.
- **One severity scale: Critical / Major / Minor**, defined only in `references/report-format.md`. Anti-patterns and failure modes assign severities using those names and point there for definitions. Never define severity levels anywhere else.
- **AP-XX and AL-XX IDs are frozen.** Never renumber or rename an existing ID; new entries append at the end of their catalog. Every cross-file mention uses "AP-XX <canonical name>" / "AL-XX <canonical name>" exactly as the owning file spells it.
- **Frontmatter `description` edits must keep the closed-skill routing intact.** The description must continue to (a) claim BOTH portfolio/multi-team work and single-team review, (b) keep the writing-new-OKRs-from-scratch exclusion, (c) name no external skill as a handoff, and (d) stay within 1,024 characters — the limit skill uploads to claude.ai and Cowork enforce; `python3 install.py check` measures it. The skill is self-contained — never reintroduce a dependency on another OKR skill.
- Findings-must-quote-evidence is a core invariant. Do not add any procedure step or template field that lets a finding exist without a verbatim quote + source ref (format in `references/report-format.md`).
- Fictional content in examples must stay clearly fictional (invented company/team names, no real people).
- **Answer keys live in `evals/keys/*.json`.** Never hand-edit a fixture below its `## Answer key` heading: change the JSON key and run `python3 evals/grader/harness.py render-key --all`; `harness.py check` fails when the generated section is stale, an evidence anchor does not resolve, or the catalog loses coverage. A recurring extra is handled with a triage entry in the key (bucket, decision, rationale, status), never by widening a row or deleting a non-defect; only a user-confirmed entry may be `known-red`, and a `skill-error` entry never can.

## Change workflow (OPSX)

This repo uses OpenSpec (OPSX) as its change-of-record system. Any non-trivial change goes through `/opsx:propose` → apply → verify → archive (or the combined `/opsx:loop`). The verify step runs the quality gate defined in `.claude/skills/openspec-loop/phases/verify-gate.md`: structural checks over the repo files (including `python3 install.py check`, the installer suite `python3 -m unittest discover -s tests`, and `python3 evals/grader/harness.py check`), plus — for skill-content changes — the harness's smoke tier (`/okr-eval smoke <slices>`) against the fixture slices that cover the touched modes, and — for publish-path changes — its lifecycle tier (`/okr-eval lifecycle`). The OPSX scaffold lives in `openspec/`; the commands and skills live under `.claude/commands/opsx/` and `.claude/skills/openspec-*`.

## Testing changes

1. Run `python3 install.py check` (the frontmatter still passes the skill-upload rules and carries a semantic `metadata.version`), `python3 -m unittest discover -s tests` (the installer suite — offline, seconds, run it on every change) and `python3 evals/grader/harness.py check` (keys valid, anchors resolve, generated answer-key sections fresh) and, if you touched the harness, `python3 evals/grader/harness.py selftest`.
2. Run the smoke tier — `/okr-eval smoke <slices>` — for the slices whose keys cover the modes your change touches: `fixture1-portfolio`, `fixture2-portfolio`, `fixture1-platform-single-team` (each key's "Modes deliberately not covered" section says which modes are the other fixture's territory; description or procedure changes run all three; anything touching mode selection or single-team behaviour includes the Platform slice). The command runs the skill as fresh subagents on your subscription and grades every report deterministically against its JSON key: all planted defects found by canonical ID, zero fabricated quotes, and no more counted findings beyond the key than its budget (intentional non-defects, off-key modes and duplicates count; confirmed known-red triage entries are reported but excluded). Read the scorecard's structure failures and warnings too.
3. If you touched the publish path — `SKILL.md`'s Step 7, the "Artifact lifecycle" section of `references/report-format.md`, the seam, a corpus under `evals/corpora/`, or `evals/lifecycle/scenarios.json` — run the lifecycle tier, `/okr-eval lifecycle`. It runs the skill as fresh subagents against a scratch corpus with a pre-seeded registry and a publish seam, one run per scenario (create, update, re-create, adopt, plus fixture-exempt — a fixture corpus with the same seam, which must publish nothing), and grades the registry each run wrote, the seam ledger, the run summary and the working folder deterministically: every deliverable reaches its declared outcome, every registered URL is verified before the run acts on it, the registry agrees with the artifact it points at, nothing forks a registered key except a single re-create stated with its reason and its deliverable, and no prior cycle's local output changes. `lifecycle-grade` exits non-zero if any scenario fails; a failure is a finding about the skill, never a reason to relax a scenario.
4. If you changed the rubric or taxonomy, verify the affected dimension/failure mode still catches its corresponding planted defect(s).
5. If you changed the `description`, sanity-check routing on three cases: a single-team prompt ("review the Payments team's OKRs") must trigger this skill, a portfolio prompt ("audit all our teams' OKRs") must trigger it, and a write-new-OKRs prompt ("draft OKRs for my team") must NOT.
6. When adding a new anti-pattern or failure mode, also plant a matching defect in one fixture, add its row (accepted IDs, evidence anchors, location, note) to that fixture's JSON key, add the new ID to the *other* key's `not_covered` list, and run `render-key --all` — the fixtures double as the eval set, and `check` enforces full-catalog coverage and the per-key partition.
7. To judge a rubric/taxonomy change, run `/okr-eval candidate` (working-tree arm only, 5 runs per slice) and read the scorecard against each key's **absolute criterion** — every planted defect found by canonical ID, zero fabricated quotes, counted findings within the budget. **That is the standing bar for "the skill delivers a good outcome" (owner's decision, 2026-09-09); a cross-model or cross-version regression verdict is not required to ship.** Two stronger options exist when you want one: a paired decision batch, `/okr-eval decision --baseline <git-ref>` (5 runs per slice per arm, old snapshot vs working tree, same model, read `comparison.json`), or `compare <batch> --baseline-batch <earlier-batch>` for an unpaired comparison against a committed baseline. Under either, a regression is a row's hit count dropping by two or more of five, a new extra or duplicate in three or more candidate runs, or any fabricated quote. Batches live under `evals/runs/`; `compare` refuses arms that ran on different models, by design.
8. The OPSX verify gate (see Change workflow) automates the structural checks, the lifecycle tier for publish-path changes, and the smoke tier scoped to the touched category for skill-content changes; the routing sanity-check (step 5) remains manual.

## Releasing

Users install and update with the one-command install, which always takes the **latest published release**. Merged changes to the skill payload (`SKILL.md`, `LICENSE`, `references/`, `examples/`) therefore reach them only when a release is cut. A merged change to `install.py` reaches every one-liner user at once, because the one-liner always fetches `main`'s installer (see the last paragraph of this section). To release:

1. Bump `metadata.version` in `SKILL.md`'s frontmatter:
   - **patch** — wording fixes, and fixture or answer-key corrections;
   - **minor** — rubric, taxonomy, procedure, report-format or `description` changes;
   - **major** — a breaking change to the report contract or the install layout.
2. Run the checks in "Testing changes", then merge. `python3 install.py check` must print the intended version.
3. `gh release create vX.Y.Z --target <merge-commit-sha> --prerelease --generate-notes`. The tag must equal `v` + `metadata.version`: the installer refuses a release whose version disagrees with its tag. A pre-release is never "latest".
4. Smoke the release into one scratch home, twice: `h=$(mktemp -d)`, then run `HOME="$h" sh -c 'curl -fsSL https://raw.githubusercontent.com/im1tta/OKR-Ninja/main/install.py | python3 -I - --release vX.Y.Z'` two times. Expect `new install` on the first run and `was X.Y.Z` on the second, for both targets.
5. Promote it with `gh release edit vX.Y.Z --prerelease=false --latest`, then smoke the unpinned one-liner the same way (a fresh home, twice).

The one-liner runs `main`'s `install.py` against every release, so `main`'s installer must always be able to install each published release. When a release changes the payload's shape (new top-level payload file, frontmatter layout), add a frozen-shape case for it to `tests/test_install.py`.
