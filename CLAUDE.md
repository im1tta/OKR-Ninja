# CLAUDE.md — for agents developing this repo

This repo is an Agent Skill ("okr-ninja") that audits OKRs for quality ("goodness") and cross-team alignment in two modes selected by team count at scope intake: **portfolio mode** (2+ teams — breadth and alignment) and **single-team mode** (one team — full-depth goodness review). The skill is closed and self-contained: it never defers OKR review to any external skill.

## File map and ownership (no duplication between files)

| File | Owns | Must NOT contain |
|---|---|---|
| `SKILL.md` | Trigger description (frontmatter) + the step-by-step review procedure, pointers to references | Rubric dimension definitions, alignment failure-mode definitions, output templates, severity definitions |
| `references/goodness-rubric.md` | The ONLY home of rubric dimensions (O1–O4, K1–K7), 0–4 scoring anchors, team-dimension aggregation and roll-up rules, and the AP-XX anti-pattern catalog | Alignment content, report/finding templates, severity-scale definitions |
| `references/alignment-taxonomy.md` | The ONLY home of AL-XX cross-team failure modes and their detection heuristics | Goodness/rubric content, report/finding templates, severity-scale definitions |
| `references/report-format.md` | The ONLY home of output/finding templates, the Critical/Major/Minor severity scale, and the source-ref format | Rubric or taxonomy definitions (it references them by ID and canonical name only) |
| `examples/sample-portfolio.md`, `examples/sample-portfolio-2.md` | Test fixtures: fictional company priorities + team portfolios with planted defects (fixture 1: Brightledger, 4 teams; fixture 2: Coppervale, 5 teams, covering the catalog modes fixture 1 leaves uncovered); each file's `## Answer key` section (planted defects, intentional non-defects, triage entries, eval criterion, slices) is **generated** from its JSON key under `evals/keys/` | Real company data; hand edits below the `## Answer key` heading (edit the JSON key, then `python3 evals/grader/harness.py render-key --all`) |
| `evals/` | The eval harness: `evals/keys/*.json` — the ONLY hand-edited source of each fixture's answer key (accepted IDs, evidence anchors, non-defects, not-covered lists, budgets, slices, triage entries); `evals/prompts/` — frozen run-prompt templates; `evals/grader/harness.py` — the deterministic, stdlib-only grader (`check`, `render-key`, `plan`, `record`, `grade`, `aggregate`, `compare`, `selftest`) with its self-test corpus under `evals/grader/selftest/`; `evals/runs/<batch>/` — committed batches (prompt, report, run.json, grade.json per run; scorecard.json, comparison.json per batch) | Skill content; rubric, taxonomy, or report-format definitions |
| `README.md` | Human-facing overview, install, usage, and the ONLY home of the product context: reader personas per mode, the target use-case (cross-cycle drift tracking) vs. what is built today, the four-job priority order that breaks depth-vs-brevity ties, and the distribution intent | Procedure details agents follow |
| `openspec/` + `.claude/` | OPSX change-of-record scaffold, commands, and skills (see Change workflow below); `.claude/commands/okr-eval.md` — the `/okr-eval` command that runs eval batches through subagents on the subscription and grades them with the harness | Skill content |

If a rubric dimension needs explaining, it goes in `references/goodness-rubric.md` and everywhere else refers to it by name. Same rule for failure modes (`references/alignment-taxonomy.md`), and for templates, severities, and source-ref formats (`references/report-format.md`).

## Editing rules

- **Keep `SKILL.md` under ~150 lines.** If an edit pushes it past that, move detail into the appropriate `references/` file instead.
- **Every rubric or taxonomy change needs a matching example in the same file.** For a goodness anti-pattern: a bad OKR (before) and its concretely rewritten form (after) — actual replacement text, not advice about writing one. For an alignment failure mode: a scenario narrative plus the detection heuristic that catches it may stand in for an after-state. A new anti-pattern or failure mode without its example does not merge.
- **One severity scale: Critical / Major / Minor**, defined only in `references/report-format.md`. Anti-patterns and failure modes assign severities using those names and point there for definitions. Never define severity levels anywhere else.
- **AP-XX and AL-XX IDs are frozen.** Never renumber or rename an existing ID; new entries append at the end of their catalog. Every cross-file mention uses "AP-XX <canonical name>" / "AL-XX <canonical name>" exactly as the owning file spells it.
- **Frontmatter `description` edits must keep the closed-skill routing intact.** The description must continue to (a) claim BOTH portfolio/multi-team work and single-team review, (b) keep the writing-new-OKRs-from-scratch exclusion, and (c) name no external skill as a handoff. The skill is self-contained — never reintroduce a dependency on another OKR skill.
- Findings-must-quote-evidence is a core invariant. Do not add any procedure step or template field that lets a finding exist without a verbatim quote + source ref (format in `references/report-format.md`).
- Fictional content in examples must stay clearly fictional (invented company/team names, no real people).
- **Answer keys live in `evals/keys/*.json`.** Never hand-edit a fixture below its `## Answer key` heading: change the JSON key and run `python3 evals/grader/harness.py render-key --all`; `harness.py check` fails when the generated section is stale, an evidence anchor does not resolve, or the catalog loses coverage. A recurring extra is handled with a triage entry in the key (bucket, decision, rationale, status), never by widening a row or deleting a non-defect; only a user-confirmed entry may be `known-red`, and a `skill-error` entry never can.

## Change workflow (OPSX)

This repo uses OpenSpec (OPSX) as its change-of-record system. Any non-trivial change goes through `/opsx:propose` → apply → verify → archive (or the combined `/opsx:loop`). The verify step runs the quality gate defined in `.claude/skills/openspec-loop/phases/verify-gate.md`: structural checks over the repo files (including `python3 evals/grader/harness.py check`) plus, for skill-content changes, the harness's smoke tier (`/okr-eval smoke <slices>`) against the fixture slices that cover the touched modes. The OPSX scaffold lives in `openspec/`; the commands and skills live under `.claude/commands/opsx/` and `.claude/skills/openspec-*`.

## Testing changes

1. Run `python3 evals/grader/harness.py check` (keys valid, anchors resolve, generated answer-key sections fresh) and, if you touched the harness, `python3 evals/grader/harness.py selftest`.
2. Run the smoke tier — `/okr-eval smoke <slices>` — for the slices whose keys cover the modes your change touches: `fixture1-portfolio`, `fixture2-portfolio`, `fixture1-platform-single-team` (each key's "Modes deliberately not covered" section says which modes are the other fixture's territory; description or procedure changes run all three; anything touching mode selection or single-team behaviour includes the Platform slice). The command runs the skill as fresh subagents on your subscription and grades every report deterministically against its JSON key: all planted defects found by canonical ID, zero fabricated quotes, and no more counted findings beyond the key than its budget (intentional non-defects, off-key modes and duplicates count; confirmed known-red triage entries are reported but excluded). Read the scorecard's structure failures and warnings too.
3. If you changed the rubric or taxonomy, verify the affected dimension/failure mode still catches its corresponding planted defect(s).
4. If you changed the `description`, sanity-check routing on three cases: a single-team prompt ("review the Payments team's OKRs") must trigger this skill, a portfolio prompt ("audit all our teams' OKRs") must trigger it, and a write-new-OKRs prompt ("draft OKRs for my team") must NOT.
5. When adding a new anti-pattern or failure mode, also plant a matching defect in one fixture, add its row (accepted IDs, evidence anchors, location, note) to that fixture's JSON key, add the new ID to the *other* key's `not_covered` list, and run `render-key --all` — the fixtures double as the eval set, and `check` enforces full-catalog coverage and the per-key partition.
6. To judge a rubric/taxonomy change, run `/okr-eval candidate` (working-tree arm only, 5 runs per slice) and read the scorecard against each key's **absolute criterion** — every planted defect found by canonical ID, zero fabricated quotes, counted findings within the budget. **That is the standing bar for "the skill delivers a good outcome" (owner's decision, 2026-09-09); a cross-model or cross-version regression verdict is not required to ship.** Two stronger options exist when you want one: a paired decision batch, `/okr-eval decision --baseline <git-ref>` (5 runs per slice per arm, old snapshot vs working tree, same model, read `comparison.json`), or `compare <batch> --baseline-batch <earlier-batch>` for an unpaired comparison against a committed baseline. Under either, a regression is a row's hit count dropping by two or more of five, a new extra or duplicate in three or more candidate runs, or any fabricated quote. Batches live under `evals/runs/`; `compare` refuses arms that ran on different models, by design.
7. The OPSX verify gate (see Change workflow) automates the structural checks and, for skill-content changes, the smoke tier scoped to the touched category; the routing sanity-check (step 4) remains manual.
